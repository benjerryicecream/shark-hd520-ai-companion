# HD520 Companion API Notes (Phase 1)

Plain copy only. No em dashes are used in this file.

## Endpoint inventory (REST, server.py)

Base: http://127.0.0.1:8791. Nothing else is served.

- GET /health: JSON {"ok": true, "app": "hd520-companion", "version": "1.0-phase1", "desktop": true/false}. No auth required.
- GET /: serves ui/index.html. No auth required for the page itself. API calls made from the page still need the token, except in desktop mode, where the page is served with the token injected (localhost only, single-user trade; see the desktop section).
- GET /api/settings: JSON {"meta_configured": true/false, "meta_source": "stored-vault"/"stored-file"/"env"/"none", "desktop": true/false, "version": "1.0-phase1"}. Auth required. Never returns the key.
- POST /api/settings/meta-key: JSON body {"key": "..."}. Stores the Meta key and returns {"meta_configured": true, "meta_source": ...}. Auth required. This is the one endpoint that accepts a key in a body.
- DELETE /api/settings/meta-key: removes the stored key and returns the new status. An environment key, if set, still applies after. Auth required.
- POST /api/shutdown: desktop mode only. Quits the app. Auth required. Returns 404 in non-desktop mode.
- POST /api/generate_cabinet: JSON body {"params": {...}} with an optional "caller" string. Returns the engine job dict: job_id, params (resolved, including the provisional list), parts, nesting, provider_record, preflight, cut_list_text, dxf_text. Auth required.
- POST /api/check_job_hd520: JSON body {"job": {...}} with an optional "caller" string. Returns the engine preflight dict: passed plus per-rule checks with status, detail, and fix text. Auth required.

Any other path returns 404. Any malformed body returns 400 with a plain error.

## Tool inventory (MCP, mcp_server.py)

Transport: JSON-RPC over stdio. One JSON object per line in, one per line out. Logs go to stderr only, never stdout. Supported methods: initialize, tools/list, tools/call, ping. Notifications (methods starting with notifications/) get no reply.

Tools (exactly two):

- generate_cabinet: input schema has params (object, required), caller (string, optional), token (string, required). Returns the job dict as both text content and structured content.
- check_job_hd520: input schema has job (object, required), caller (string, optional), token (string, required). Returns the preflight dict as both text content and structured content.

Unknown tool, bad token, or bad params returns a JSON-RPC error object. No traceback with secrets is ever returned.

## Auth rules

REST: header X-API-Token or Authorization: Bearer must match env HD520_API_TOKEN. Wrong or missing token returns HTTP 401 with a JSON error and is logged to stderr without the token value. No token, no calls, including from localhost.

MCP: tools/call arguments must include a "token" field matching env HD520_API_TOKEN (a top-level token on the call is also accepted). Bad or missing token returns JSON-RPC error code -32001.

Token generation: if HD520_API_TOKEN is unset at startup, each server generates a random token, prints it once, and requires it. REST prints it once to stdout with a clear label. MCP prints it once to stderr, never stdout. A token generated by one server is not shared with the other; each process has its own unless HD520_API_TOKEN is set in the environment for both.

Request bodies never accept API keys, with one exception: POST /api/settings/meta-key is the Settings page's save path, localhost only, with a valid API token. A tool body (REST) or call arguments (MCP) containing an api_key style field is refused with a plain error. Keys live in server environment variables or in the keystore (see the desktop section). The UI's only API key input is the Settings Meta key field.

## Meta rule (no silent cloud)

Provider "meta" is used only when the caller requests provider "meta" AND a Meta key is configured. The effective key, in precedence order, is: a key stored through the Settings page (keystore.py), env HD520_META_API_KEY, env META_API_KEY. The server maps the resolved key to the engine's META_API_KEY variable before every Meta call, so a key saved through Settings works without a restart. The MCP server resolves the key at startup, so a key saved through Settings is picked up on the next MCP start. If Meta is requested but no key is configured, REST returns HTTP 400 and MCP returns a JSON-RPC error, both saying Meta is not configured. The local parser is never silently run and labeled Meta.

Engine behavior, stated honestly: the engine runs the Meta brief parse only when brief_text is supplied in params. A params-only request with provider "meta" records provider "meta" in provider_record without making a model call, because there is no brief to parse. Explicit params always win over parsed params. A failed Meta call raises; it never falls back to local parsing and never retries on another provider.

## Binding rule

REST binds 127.0.0.1 port 8791 only. Never 0.0.0.0. No Tailscale, no public binding, no port forwarding. Localhost-only is a locked decision; Tailscale is undecided and must not be enabled. MCP uses stdio only and opens no network port.

## Logging shape

File: jobs/api_log.jsonl. One JSON line per API call (REST and MCP), appended in call order. Fields:

- timestamp: UTC ISO timestamp.
- caller: the "caller" field from the body or arguments, else "unknown".
- tool: generate_cabinet or check_job_hd520.
- job_id: the job id, or null when no job exists (for example a 401 or a bad request).
- provider: provider from the job provider_record, or null.
- model: model from the job provider_record, or null.
- preflight_passed: true, false, or null.
- status: "200", "400", "401", "500", "502", or an MCP error label.

Never logged: tokens, API keys, or secret values. A secret-scan failure is logged by rule name only, never with the secret.

## Job storage (provisional)

Each generated job is saved to jobs/job-YYYYMMDD-HHMMSS-<slug>.json, where the slug comes from params job_name or, when no job name is given, from the layout, lowercased with non-alphanumeric runs replaced by hyphens. This folder and naming are PROVISIONAL, pending the owner's decision. Job files contain engine output only: no token, no key, and no caller credential of any kind. In desktop mode and in the packaged exe, jobs live under the per-user data dir instead (Windows: %APPDATA%\HD520Companion\jobs), because the exe runs from a temporary extraction dir that is wiped on exit.

## Desktop packaging

Entry: desktop.py. No args starts the REST server with --desktop and opens the UI in the default browser once /health answers. --mcp runs the MCP server over stdio from the same binary. Run from source with `py desktop.py` (or run-desktop.bat); no build is needed to try desktop mode.

Build: hd520-companion.spec, via `py -m PyInstaller hd520-companion.spec` or build.bat, run on the Windows desktop. PyInstaller does not cross-compile. Output: dist\HD520Companion.exe, one file, no console window. Data files (ui/index.html, engine/tools_data.json) are bundled mirroring the source tree, because the servers locate them relative to their own files. build/ and dist/ are gitignored.

Key storage: keystore.py. On Windows the key goes to Windows Credential Manager (ctypes, no new dependency), target HD520Companion/MetaApiKey, generic credential, local-machine persistence. Anywhere else, or if the vault call fails, the key goes to a 0600 file at <config>/HD520Companion/meta_key. Delete clears both stores. Settings status reports only whether a key is stored and where, never the key. The secret scan before returning exports covers the resolved key, so a stored key can never leak into a cut list or DXF.

Desktop token trade, stated plainly: in desktop mode the UI page is served with the API token injected. The server still binds 127.0.0.1 only, and the token still gates every API call from any other client, but any process on the same machine that can fetch the page can read the token from it. That is acceptable for a single-user desktop app and is not acceptable for any shared or networked setup, which is why the app stays localhost-only.

## No-machine-control audit statement

No machine-control verb exists in this app. There is no endpoint or tool for start, jog, pause, home, spindle, or export bypass, and no endpoint or tool that moves, powers, or commands the Shark HD520 in any way. The only outputs are job JSON, plain text cut lists, and DXF text for file import into VCarve. The .tap post step belongs to a later phase and is not present here. Phase 1 tools are exactly generate_cabinet and check_job_hd520. No export endpoints exist in Phase 1: export_tap and export_svg_dxf are later phases.

## Secrets handling

Before any generated job is returned, every export string (dxf_text and cut_list_text) is scanned with the engine scan_for_secrets function against the server token and the Meta key (when set). If a hit occurs, the server returns HTTP 500 (REST) or a JSON-RPC error (MCP), logs the rule name only, and withholds the export. The secret value is never included in a response, a log line, or a job file.

## UI-path and MCP-path parity

Parity is achieved by sharing one code path: both server.py and mcp_server.py import generate_cabinet and check_job_hd520 from the same engine package and call them with the caller's params or job unchanged (after stripping auth and logging fields, which the engine never sees). Neither server re-implements part building, nesting, preflight, or export logic. The parity test in the next stage asserts identical parts lists: the same params through the REST endpoint and through the MCP tool must return the same parts list, nesting, and preflight. Any difference between the two paths would be a bug in the servers, not an engine difference, because the engine function is the same in both cases.
